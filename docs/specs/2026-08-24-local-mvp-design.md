# 暗房本地 MVP 设计规格

日期：2026-08-24  
状态：待用户审阅  
工作名：暗房（可更换，不写入数据契约）

## 1. 本阶段目标

把现有模型评测能力接入一个可实际使用的本地网页，完成单张照片从选择、可选创作意图、压缩分析、结果阅读到删除记录的闭环。

本阶段不是另做一个评测页面，也不加入账户、支付、社区、RAG、训练或微调。现有 `experiments/ai-analysis-eval` 保留为模型回归工具。

## 2. 名称与界面语气

界面暂用“暗房”，不使用“AI 摄影教练”作为主品牌。需要说明能力来源时，在次要位置写“AI 辅助分析”，不把 AI 放在页面主标题中。

视觉继续采用暗房语境：近黑背景、温和纸白、低饱和暗铜色操作提示、灰绿色/暖灰金/砖红色评分状态。避免高亮霓虹、蓝紫渐变、发光卡片和密集仪表盘。页面通过留白、细分隔线和字体层级建立高级感，不把每个区块都装进卡片。

## 3. 核心流程

1. 用户选择一张本地照片。
2. 页面完整显示照片，不裁掉任何边缘。
3. 用户可选填写摄影类型、创作意图和希望重点关注的方面。
4. 客户端生成用于分析的压缩副本，并明确显示“原图未修改”。
5. 本地服务通过统一模型适配层调用 Qwen，校验结构化结果。
6. 页面展示照片、评分刻度、事实、解释、意图关系、替代解读和建议。
7. 用户可以关闭标注、预览可撤销裁切、记录逐条反馈，并删除本地分析记录。

创作意图完全选填。不填写时，系统按通用摄影基础分析，不能猜测用户意图。

## 4. 页面结构

### 4.1 输入页

桌面端采用左右两栏：照片区约 55%，输入区约 45%。照片是第一视觉焦点，输入区保持安静、紧凑，不做营销式首屏。

移动端改为上下结构：照片在上，输入在下；操作按钮固定宽高，加载文字变化不能引起布局跳动。

输入项包括：

- 照片选择：JPEG、PNG、WebP；HEIC 在实现前验证当前浏览器和服务端解码方案。
- 摄影类型：街头、纪实、人像、风光、城市空间、实验/抽象、不确定。
- 创作意图：最多 200 字，选填。
- 希望重点关注：构图、光线、色彩、叙事、技术质量，可多选，选填。

“重点关注”只改变解释篇幅和建议排序，不改变模型看到的画面事实，也不人为抬高或压低评分。

### 4.2 分析状态

只展示真实阶段：处理图片、读取画面、校验结果、整理点评。没有后端进度时不显示伪造百分比。超时后允许重试，不能要求用户手动 `Control-C` 再调用。

### 4.3 结果页

桌面首屏采用“左侧照片工作区 + 右侧阅读区”。照片区在滚动前半段保持可见，便于对照文字证据；窄屏取消吸顶，避免图片遮挡内容。

右侧顺序：

1. 一句话结论和整体完成度。
2. 五维评分刻度。
3. 可直接观察的事实。
4. 基于摄影知识的解释。
5. 创作意图与画面证据的关系（仅在填写意图时显示）。
6. 主观判断与另一种合理解读。
7. 可执行建议，区分“拍摄时”和“后期可调整”。

裁切与标注是照片工作区的工具，不混入评分正文。裁切默认关闭，用户主动预览后才显示遮罩；所有操作只作用于预览副本。

## 5. 评分可视化

评分不能只显示数字。整体完成度保留一个克制的小号数字，五个分项同时显示：

- 维度名称
- 0 到 100 的整数
- 水平刻度条
- 置信度文字或信息入口
- 一句证据摘要

刻度条规则：

- 85 到 100：灰绿色 `#6f806d`
- 75 到 84：暖灰金 `#a58b62`
- 0 到 74：低饱和砖红 `#98584f`
- 未评分或证据不足：中性灰，不补造分数

填充宽度严格对应分数，轨道使用低对比深灰。颜色只用于快速扫读，不显示“差”“失败”等标签。动画只在结果第一次出现时从 0 到真实值完成一次，持续约 500 毫秒；尊重系统的“减少动态效果”设置。

整体分数由五个分项按已批准规则计算，界面不重复“总分仅作快速索引”等模板句。分数旁提供一次性的说明入口，解释它是阅读索引而不是审美裁决。

## 6. 不同尺寸照片的显示与传输

### 6.1 完整构图优先

照片容器读取实际宽高比，使用 `object-fit: contain`，任何横图、竖图、方图或全景图都必须显示完整边缘。容器使用深色中性底，不拉伸、不填充裁剪、不用背景模糊补边。

建议约束：

- 桌面输入页：最大高度 `72vh`，最大宽度为照片栏宽度。
- 桌面结果页：最大高度 `calc(100vh - 140px)`。
- 移动端：最大高度 `62vh`，同时保证下方操作入口可见。
- 极端全景或长竖图可以缩小，但不能截断；用户可点开放大查看。

标注坐标使用 0 到 1 的归一化坐标，并绑定图片实际渲染区域，不能绑定外层容器。这样 `contain` 产生留边时，框线仍与照片对齐。

### 6.2 分析副本

选择照片后生成独立分析副本：

1. 校正 EXIF 方向。
2. 保持原始宽高比。
3. 长边超过 2048px 时缩到 2048px；较小图片不放大。
4. 优先编码为 JPEG 或 WebP，初始质量约 0.86；若仍超过约 2.5MB，逐级降到最低约 0.72。
5. 只把分析副本传给模型，原文件不修改、不覆盖。
6. 删除精确 GPS 和不必要 EXIF；记录传输尺寸、耗时和模型延迟，不记录照片内容。

压缩目标是降低上传与模型等待时间，不改变完整构图。页面预览可以使用同一份高质量副本，用户仍能看到整张照片；需要查看细节时提供局部放大，而不是为显示清晰度上传超大原件。

若压缩失败、格式无法解码或画质低到不足以可靠判断，明确提示并停止分析，不能静默使用错误方向或残缺图片。

## 7. 创作意图如何影响点评

分析分为两层：

1. 事实层只根据图片提取主体、位置、光线、颜色、空间与技术现象，不读取创作意图来改写事实。
2. 解释层再结合事实和可选意图，判断画面是否支持该表达，并生成建议。

填写意图后，结果单独输出：

- 支持程度：支持、部分支持、证据不足。
- 支持证据：画面中哪些事实与意图一致。
- 张力或偏差：哪些视觉关系可能削弱意图。
- 另一种合理理解。

构图、光线、色彩与技术质量仍依据画面证据评分。创作意图不直接加分，也不因为模型赞同意图而改变事实；它只影响叙事解释、建议优先级和措辞。用户要求重点关注某维度时，也只增加该部分细节，不改变评分计算。

## 8. 模型与校验边界

- 页面业务代码不直接调用供应商 SDK；本地服务通过统一模型适配接口调用 Qwen。
- 模型输出先经过 schema、分数、坐标、置信度和裁切损失校验，再渲染。
- 不可靠引导线、主体框或裁切框降级为文字；不能为了展示功能强行画线。
- 事实与意图冲突时保留冲突，不迎合用户。
- API 首次调用慢的问题在本地服务中通过明确超时、有限重试和状态提示处理，不依赖终端人工中断。

## 9. 与旧版本的关系

旧交互原型位于 Git 分支 `feat/dynamic-frontend-prototype` 的 `apps/web`。可复用内容包括：

- 暗房配色和基础排版
- 上传/意图输入页
- 结果页双栏结构
- 五维评分条
- 图层开关、裁切预览和参数建议交互
- Next.js、React、Zod 和测试配置

需要重做或补齐：

- 从固定样例改为真实本地照片选择
- 完整画幅适配与压缩管线
- Qwen 适配层和真实状态
- 新的意图关系结构
- 模型输出 schema 与现有评测规则衔接
- 本地记录与删除
- 移动端竖图、全景图和超大图的视觉回归测试

## 10. 首版验收条件

- 横图、竖图、方图、全景图均完整显示，框线位置不偏移。
- 一张 20MB 级别照片不会以原始体积直接传给模型。
- 五维分数均有可视化刻度、证据和可访问文本。
- 未填写意图时不出现虚构意图；填写后事实层不被意图改写。
- 结果不重复固定总分免责声明。
- 低置信度框线不会为了界面丰富而强制出现。
- 用户无需在终端输入长命令或通过中断后重试才能完成一次分析。
- 原图不被裁切或覆盖，分析记录可以删除。
- 桌面与移动端均完成真实图片视觉验证。
